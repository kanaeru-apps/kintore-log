# レビュー依頼：iOS（Capacitor）でローカル通知が一切配信されない

このファイルは、別のAIにセカンドオピニオンをもらうための資料です。
リポジトリを見られない前提で、**判断に必要と考えた主要コードと事実をここに転記**しています。
推測と確認済みの事実は明確に分けて書いています。

---

## 0. 一行で言うと

**Capacitor（iOS）製のアプリで `LocalNotifications.schedule()` を使ったタイマー通知が、前面・背面のどちらでも1件も配信されない。**
ただし**アプリを開いている間のアプリ内アラーム音と振動は正常に動く**。

---

## 2. 症状（実機での観測事実）

TestFlight の v0.13.4 で、ユーザー本人が実機テストした結果です。

| 確認したこと | 結果 |
|---|---|
| タイマー開始 → すぐホーム画面に戻る → 終了時刻に通知が来るか | ❌ **通知が来ない。音も鳴らない** |
| アプリを開いている間、終了時に音が鳴るか・振動するか | ✅ **音も振動も正常** |
| アプリを開いたまま待つ → 通知バナーが出るか | ❌ **バナーが出ない**（音が二重になることもない） |

つまり **「アプリ自身が鳴らす音」は動いていて、「OSが出す通知」だけが前面・背面ともゼロ**。

### 重要：診断値がまだ取れていない

アプリ内に診断画面（後述）を作ってありますが、**ユーザーからその値をまだもらえていません**。
したがって以下は**未確認**です：

- `checkPermissions()` が `granted` を返しているか
- `schedule()` のJS Promiseがresolveされたか（`soundDiag.sched` の値。後述のとおり、OSが予約を受理したことまでは保証しない）
- `getPending()` に予約が入っているか
- iPhone 側の通知設定（バナー/サウンド/要約）がどうなっているか

## 3. 経緯（いつ壊れたか）── いちばん重要な手がかり

| 版 | 変更内容 | 実機での結果 |
|---|---|---|
| v0.13.0 | アプリ内アラーム音の修正（AVAudioSession を `.playback` に） | アプリを開いている間の音は ✅。**閉じていると通知が来ない** ❌ |
| **v0.13.1** | `schedule()` の失敗を握り潰していた `catch` をやめ、診断（予約の成否／`getPending()`）を追加 | ✅ **アプリを閉じていても通知バナーが届いた**（ただし**無音**） |
| **v0.13.2** | **通知に `sound` を付けた**（`notif.sound = "beep.wav"`）＋WAVをXcodeのResourcesに同梱＋自前プラグイン `AlarmAudioPlugin` 追加（`installSounds` / `soundFiles` / `notificationSettings`） | ❌ **通知が一切来なくなった**（v0.13.1 で出ていたバナーも消えた） |
| v0.13.3 | 原因を「`ensureNotificationSounds()` がネイティブ呼び出しで返ってこず、その完了を待ってから `schedule()` していたので予約に到達していなかった」と判断し、タイムアウトを追加 | ❌ 直らず |
| v0.13.4 | 待ち合わせを全廃（**何も待たずに即 `schedule()`**）。終了時の `cancel()` をやめる等、通知まわり6件を修正 | ❌ **直らず（＝上記2章の症状）** |
| v0.13.5 | 原因を画面に出す版（警告バー・`getDeliveredNotifications` 追加）。**まだ実機で試していない** | 未検証 |

**注目してほしい点：v0.13.1（動いた）から v0.13.2（全停止）への変更には「通知への `sound` 追加」が含まれます。**
ただし、この版間ではWAVのResources登録、自前プラグイン追加、音源コピー・診断経路の変更も同時に入っており、`sound` だけを変えたA/B比較ではありません。したがって、時系列上の強い相関はありますが、現時点では `sound` を原因と断定できません。
v0.13.3 で立てた「待ち合わせが原因」という説明は、v0.13.4 で待ち合わせを完全に排除しても直らなかったため、**少なくとも唯一の原因ではなかった**ことになります。

  var TEST_NOTIF_ID = 2;
  var notifPermissionAsking = false;
  var PERM_WAIT_MS = 20000;

  function isNativeApp() {
    try {
      return !!(window.Capacitor && typeof window.Capacitor.isNativePlatform === 'function'
                && window.Capacitor.isNativePlatform());
    } catch (e) { return false; }
  }

  var nativePluginCache = {};
  function nativePlugin(name) {
    if (Object.prototype.hasOwnProperty.call(nativePluginCache, name)) return nativePluginCache[name];
    var p = null;
    try {
      var C = window.Capacitor;
      if (C && typeof C.registerPlugin === 'function') {
        p = (C.Plugins && C.Plugins[name]) || C.registerPlugin(name);
      }
    } catch (e) { p = null; }
    nativePluginCache[name] = p;
    return p;
  }

  /* 返ってこないネイティブ呼び出しで処理全体が止まらないようにする */
  function withTimeout(promise, ms, fallback) {
    return new Promise(function (resolve) {
      var done = false;
      var t = setTimeout(function () {
        if (done) return;
        done = true;
        resolve(fallback);
      }, ms);
      Promise.resolve(promise).then(function (v) {
        if (done) return;
        done = true; clearTimeout(t); resolve(v);
      }, function () {
        if (done) return;
        done = true; clearTimeout(t); resolve(fallback);
      });
    });
  }

  function ensureNotifPermission() {
    var ln = nativePlugin('LocalNotifications');
    if (!ln) return Promise.resolve(false);
    return Promise.resolve()
      .then(function () { return ln.checkPermissions(); })
      .then(function (r) {
        if (r && r.display === 'granted') return true;
        if (r && r.display === 'denied') return false;
        if (notifPermissionAsking) return false;
        notifPermissionAsking = true;
        return ln.requestPermissions().then(function (r2) {
          notifPermissionAsking = false;
          return !!(r2 && r2.display === 'granted');
        }, function () {
          notifPermissionAsking = false;
          return false;
        });
      })
      .catch(function () { return false; });
  }

  function alarmFileName(key) { return key + '.wav'; }   // 'beep' -> 'beep.wav'

  function buildNotif(id, body, at) {
    var notif = {
      id: id,
      title: '筋トレLog',
      body: body,
      schedule: { at: at, allowWhileIdle: true }    // at は JS の Date オブジェクト
    };
    if (timerSettings.soundOn) notif.sound = alarmFileName(timerSettings.sound);  // 既定 'beep.wav'
    return notif;
  }

  function pushNotif(ln, id, body, atMs) {
    var at = new Date(atMs);
    var notif = buildNotif(id, body, at);
    soundDiag.sched = '予約中… ' + hhmmss(at);
    try {
      Promise.resolve()
        .then(function () { return ln.schedule({ notifications: [notif] }); })
        .then(function () {
          soundDiag.sched = 'OK ' + hhmmss(at) + ' / ' + (notif.sound || '音なし');
          return refreshPendingDiag();
        })
        .catch(function (e) {
          soundDiag.sched = 'NG: ' + errText(e);
          noteAppError('通知の予約', e);
        })
        .then(renderSoundDiag);
    } catch (e) {
      soundDiag.sched = 'NG: ' + errText(e);
      noteAppError('通知の予約', e);
    }
  }

  /* 予約は「まず出す、あとで直す」。
     iOSのWebViewはアプリが背面に回るとJSを止めるため、許可確認や音の準備の完了を
     待ってから予約すると、待っている間に閉じられた回は schedule() に到達しない。 */
  function scheduleTimerNotification(endAtMs) {
    if (!isNativeApp()) { soundDiag.sched = '—（ブラウザ版）'; return; }
    var ln = nativePlugin('LocalNotifications');
    if (!ln) { soundDiag.sched = 'NG: 通知プラグインが読み込まれていない'; return; }
    if (!timerSettings.notifyOn) { soundDiag.sched = '—（システム通知がOFF）'; return; }
    if (endAtMs <= Date.now()) { soundDiag.sched = 'NG: 終了時刻が過去'; return; }

    // ① 何も待たずに予約する
    pushNotif(ln, TIMER_NOTIF_ID, '休憩終了！ 次のセットへ', endAtMs);

    // ② 許可はそのあとで確認し、取れたら同じidで出し直す
    withTimeout(ensureNotifPermission(), PERM_WAIT_MS, null)
      .then(function (granted) {
        if (granted === false) { soundDiag.sched = 'NG: 通知が許可されていない'; return; }
        if (!timer.running || timer.paused || timer.finished || timer.endAt !== endAtMs) return;
        if (endAtMs - Date.now() < 1500) return;
        pushNotif(ln, TIMER_NOTIF_ID, '休憩終了！ 次のセットへ', endAtMs);
      })
      .catch(function (e) { noteAppError('通知の許可確認', e); });

    // ③ 音の準備は予約と切り離して進める
    ensureNotificationSounds();
  }

  function cancelTimerNotification() {
    var ln = nativePlugin('LocalNotifications');
    if (!ln) return;
    try {
      ln.cancel({ notifications: [{ id: TIMER_NOTIF_ID }] }).catch(function () { /* noop */ });
    } catch (e) { /* noop */ }
  }

  function clearDeliveredTimerNotification() {
    var ln = nativePlugin('LocalNotifications');
    if (!ln || !ln.removeDeliveredNotifications) return;
    try {
      var r = ln.removeDeliveredNotifications({ notifications: [{ id: TIMER_NOTIF_ID }] });
      if (r && r.catch) r.catch(function () { /* noop */ });
    } catch (e) { /* noop */ }
  }

### 重要：`schedule()` の成功表示には競合がある

上記実装では `UNUserNotificationCenter.current().add(request)` の完了ハンドラを待たず、ループ終了後に `call.resolve(...)` しています。
そのためJS側で `schedule()` がresolveされても、それは**要求を組み立てて `add()` を呼び出した**ことまでしか示さず、OSが予約を受理したことは保証しません。`add()` が後からエラーになった場合、すでにresolve済みのJS Promiseへ `call.reject(...)` が届かない可能性があります。

同じ理由で、`schedule()` のresolve直後に呼んでいる `getPending()` は、`add()` の完了前に実行される競合があります。現在の `soundDiag.sched = "OK"` と直後のpending件数だけでは、予約成功・失敗を一意に判定できません。

## 8. こちらの仮説（いずれも**未確証**）

### 仮説A：端末側の状態（許可されていない／バナーやサウンドが個別にオフ／要約に入っている）

- 根拠：前面・背面ともゼロという症状は「OSレベルで止められている」と整合する
- 弱点：**v0.13.1 では同じ端末で通知が出ていた**。その後ユーザーが設定を変えたという情報はない

### 仮説B：`sound` 指定が原因

- 根拠：v0.13.1（`sound` なし）→出る、v0.13.2（`sound: "beep.wav"` 追加を含む）→出ない、という**時系列の一致**
- 弱点：版間には他の変更も多数あり、`sound` 単独の比較ではない。Appleの公開ガイドでは、適切なカスタム音源が見つからない場合はデフォルト音を再生すると説明されているため、単純な「音源を読めないため通知全体が消える」とは整合しにくい
- Apple一次資料：https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/SchedulingandHandlingLocalNotifications.html

### 仮説C：許可を取る前に `schedule()` している設計自体の問題

- 現在の設計は「まず `add()`、あとで `requestAuthorization()`」
- `authorizationStatus == .notDetermined` の状態で `UNUserNotificationCenter.add()` した予約が、**その後に許可が下りたときに配信されるのか**を確認できていない
- もし「`add()` 時点の許可状態で判定される」なら、初回起動時の予約はすべて無効になる
- Appleの公開ドキュメントは、ローカル通知を予約する前に認可を要求するよう案内している。現在の順序は少なくとも推奨順序とは逆になっている
- Apple一次資料：https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/requestauthorization(options:completionhandler:)

### 仮説D：Capacitor 8.2.1の `schedule()` 完了通知が早すぎて、実際のadd失敗を観測できていない

- 根拠：5章の実装では `UNUserNotificationCenter.add()` の完了を待たずに `call.resolve()` している
- 影響：JSでは `OK` と表示されても、その後のネイティブエラーが見えない可能性がある。直後の `getPending()` もadd完了前に走りうる
- 弱点：これは「診断が成功を誤表示する」説明にはなるが、addが実際に失敗している理由そのものは別途特定が必要

### 仮説E：`AVAudioSession` を `.playback` にしていることの副作用

- 起動時と `applicationDidBecomeActive` のたびに `.playback` + `setActive(true)` を張っている
- これが通知音や通知そのものの挙動に影響する可能性を否定できていない（`.mixWithOthers` は付けている）

|---|---|---|
| `schedule = OK` | プラグインが要求を組み立て、`UNUserNotificationCenter.add()` を呼んだ | add完了前にresolveされるため、OSによる受理・後発エラーは未確認 |

## 10. レビュー結果と対応（2026-08-17 / v0.13.6）

この資料でレビューを受け、**要修正3件**の指摘があった。すべて実コードで裏を取ったうえで v0.13.6 で対応済み。
詳細は `DESIGN.md` の Phase 9.10 を参照。

| # | 指摘 | 裏取り | 対応 |
|---|---|---|---|
| 1（高） | `schedule()` の resolve を「予約成功」として扱っている。直後の `getPending()` も競合する | **正しい**。プラグインの `schedule` は `center.add(request){...}` のコールバック**外**で `call.resolve` している。さらに add 失敗時の `call.reject` は resolve 済み呼び出しへの空振りで、**JSには失敗が届かない**（指摘より深い） | resolve は「受付」までとし、`getPending()` にidが現れるまで 400ms×最大6回 聞き直して確認できたときだけ `OK（OS確認済み）` と書く。結果は 確認済み / OSに入っていない / 聞けなかった / 時刻経過 の4通りに分ける |
| 2（高） | `presentationOptions` に `"sound"` が無く前面通知が無音。診断に出ていない | **正しい**。`LocalNotificationsHandler.willPresent` は配列に無いものを入れないため、明示配列＝明示的な抑止 | 無音は**意図した設計**（前面はアプリ内アラームが鳴るので二重にしない）。レビューの2案目に従い、診断に「アプリを開いている時の通知」欄を新設して明記した |
| 3（中） | `fillDiag()` が失敗時に古い正常値を残す | **正しい**。`catch` で `answered = true` にするだけで値を更新していなかった | `fillDiag(sel, key, work)` に変更し、失敗は `NG: 理由`、時間切れは `確認が返ってきません（時間切れ）` で必ず上書きする |

**レビューでは挙がらなかったが、修正の検証中に見つけて直したもの**

- 予約は「まず出す → 許可が取れたら出し直す」の2段構えで、各段が数百ミリ秒の確認を伴う。
  先に始まった確認が後から返り、より新しく確定した `NG: 通知が許可されていない` を `OK` で上書きしていた。
  書き手に通し番号を配り、追い越された書き手は黙るようにした。

**採らなかった案**：指摘1の「ネイティブ側で add 完了結果を直接取得・保存する」。
Capacitor 内部の `add` 呼び出しには外から割り込めず、自前の予約経路をもう1本作ることになる。
ビルド直前に本番経路を増やす risk のほうが大きいと判断した。
`getPending()` による確認でも「add が失敗した」という**結果**は確実に捉えられる（取れないのは失敗理由の文字列だけ）。
